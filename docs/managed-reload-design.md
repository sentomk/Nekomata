# Managed hot-reload design

Status: proposed design. This document defines the intended contract; it does
not claim that every item is implemented today. Section 17 records the current
gap and migration path.

Concrete build-adapter contracts are specified in:

- [CMake project integration](cmake-integration-design.md);
- [GN project integration](gn-integration-design.md);
- [Meson project integration](meson-integration-design.md).

This document is authoritative for runtime, transaction, identity, and
publication semantics. Each adapter document is authoritative for its own
build-facing interface.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
express requirements on the proposed design.

## 1. Objective

An application should be able to opt into Nekomata without knowing where its
build system stores object files, depfiles, or publication markers.

The same model must cover:

- a reloadable group containing one translation unit;
- groups containing multiple translation units;
- projects with heterogeneous compile configurations and generated sources;
- atomic cross-TU replacement;
- an application-controlled safe point in multithreaded programs;
- CMake, GN, and Meson without build-system-specific runtime code;
- templates and supported optimized builds;
- an optional TUI that requests, but does not perform, an update.

The ordinary runtime integration is:

```cpp
auto backend = neko::elf::create_backend();
neko::reload_session session{std::move(backend)};
session.watch();

while (running) {
  application_reload_barrier barrier;
  const neko::update_result result = session.update();
  report(result);
}

session.unwatch();
```

The build integration decides what to rebuild. Nekomata prepares and applies a
complete generation. The application decides where `update()` is safe.

## 2. Non-goals

Nekomata is not a build system. Its runtime MUST NOT:

- invoke a compiler or linker;
- reconstruct compiler commands;
- infer arbitrary object paths from source paths;
- replace the native dependency graph with a source watcher;
- suspend application threads automatically;
- promise reload across arbitrary ABI-breaking edits;
- expose a supported driver CLI.

Programs under `tools/` remain development infrastructure. Build adapters may
invoke private helpers, but those helpers are not a public product surface.

`unwatch()` stops future observation. It MUST NOT restore old machine code or
roll application state back.

## 3. Model

### 3.1 Translation unit

A translation unit is one compiler input after preprocessing.

### 3.2 Reload unit

A `reload_unit` is a build declaration containing translation units with one
coherent compile configuration. It normally maps to one native object target.

Separate units preserve meaningful differences: C and C++ settings, generated
source dependencies, instrumentation, defines, include paths, or other target
properties.

### 3.3 Reload group

A `reload_group` contains one or more reload units and is the atomic
publication and commit boundary.

Membership is fixed for the lifetime of a running process. Changing membership
changes compatibility identity and requires rebuilding and restarting the
process.

Single-TU is not a separate runtime mode. It is a group with one object.

### 3.4 Generation

A generation is an immutable, complete snapshot of every object in one reload
group. It is never a delta. A diagnostic list may say what changed, but that
list does not define completeness.

A generation is committed in full or not at all. No object or function from a
rejected generation may become active.

### 3.5 Group descriptor

A `group_descriptor` is generated by the build adapter and linked into the
application. It describes group identity, exact membership, compatibility, and
where compatible generations are published. Ordinary application code does
not construct it.

## 4. Ownership

The build system owns:

- header, generated-file, and source dependencies;
- compiler selection and effective compile configuration;
- rebuilding affected translation units;
- materializing every object in a complete generation;
- atomic publication;
- generation and embedding of group descriptors.

The application owns:

- `reload_session` lifetime;
- serialization of calls to its public API;
- the safe point at which `update()` may redirect code;
- synchronization of application threads and state;
- presentation or logging of reload results.

Nekomata owns:

- discovery and validation of published generations;
- concurrent preparation of candidate code;
- rejection of incomplete or incompatible input;
- transactional commit within each reload group;
- rollback of a failed commit attempt;
- stable diagnostics and immutable snapshots.

The build system already has the authoritative dependency graph. Only the
application knows when its threads may safely cross a replacement boundary.

## 5. Managed runtime API

```cpp
namespace neko {

class generation_source;

class reload_session {
public:
  explicit reload_session(backend_bundle backend,
                          session_options options = {});
  explicit reload_session(backend_bundle backend,
                          std::unique_ptr<generation_source> source,
                          session_options options = {});

  void watch();
  void watch(std::string_view group_id);

  void unwatch();
  void unwatch(std::string_view group_id);

  [[nodiscard]] update_result update();
  [[nodiscard]] session_snapshot snapshot() const;
};

} // namespace neko
```

`watch()` enables every embedded group visible when the session is initialized.
`watch(group_id)` enables one named group. The zero-argument and named forms
are the same logical operation with different scope.

`unwatch()` disables every group. `unwatch(group_id)` disables one group.
Disabling prevents new discovery and discards uncommitted prepared work. It
does not undo an applied generation.

These four operations are idempotent for known groups. An unknown group ID is
a configuration error. Re-enabling a group resumes from its existing consumer
cursor and MUST NOT replay generations observed before it was disabled.

`watch()` activates discovery and preparation. Routine file I/O, parsing,
symbol resolution, relocation, and validation SHOULD happen on an internal
worker. `update()` only commits work that is already prepared; it MUST NOT
invoke a build or wait for one.

`snapshot()` returns an immutable value and MUST NOT expose references into
mutable session state.

Calls to a session's public API require external serialization. Nekomata
synchronizes its internal worker; it does not make concurrent public calls
valid implicitly.

Calling `update()` with no enabled group is a programming error. Session
destruction stops and joins the preparation worker.

The initial implementation discovers descriptors linked into the main program
at startup. Dynamic descriptor registration from later-loaded libraries is not
supported yet.

### 5.1 Low-level generation sources

Manual integrations select a generation source when constructing the session.
They do not add path-shaped overloads to `watch()`:

```cpp
auto source = std::make_unique<manifest_generation_source>(
    manifest_path, std::move(planner));

reload_session session{
    std::move(backend),
    std::move(source),
};

session.watch();
```

An `object_generation_source` may provide the corresponding single-object
escape hatch. These source types are not used by managed examples. Existing
path-shaped `watch()` overloads and `generation_watch` should be deprecated
after their source-based replacements ship. In particular,
`watch(std::filesystem::path)` MUST NOT coexist with
`watch(std::string_view group_id)`: a string literal would be ambiguous in both
the type system and the reader's mental model.

## 6. Result and error contract

Routine artifact failures are values, not exceptions:

```cpp
enum class update_status : std::uint8_t {
  applied,
  rejected,
};

struct update_event {
  update_status status;
  std::string group_id;
  std::string generation_id;
  reload_error_code code;
  std::string message;
  std::size_t redirected_function_count;
};

struct update_result {
  std::vector<update_event> events;
};
```

An empty event list means nothing was ready. A malformed manifest, missing
member, digest mismatch, compatibility mismatch, unresolved symbol, or failed
transaction produces a `rejected` event and leaves the old generation active.

Programming errors and failures that make the session unusable may throw.
Examples are conflicting embedded descriptors, an unknown group passed to
`watch(group_id)`, a broken internal invariant, or unrecoverable resource
failure. A fatal worker error is retained and reported by the next serialized
public call; it MUST NOT escape the worker and terminate the process.

Events are ordered lexicographically by `group_id`, independent of link order,
filesystem iteration, and worker scheduling.

`session_snapshot` reports each group as `idle`, `preparing`, `ready`, or
`failed`, plus its last observed and last applied generation. It is the input
for logs, tests, and the optional TUI.

## 7. Descriptor and identity

Each embedded descriptor contains at least:

- `group_id`: a stable, process-unique logical name;
- `members`: the exact, ordered set of logical object keys;
- `publication_key`: a logical key for the generation stream;
- `baseline_sequence`: the stream high-water mark represented by the linked
  executable;
- `compatibility_id`: an opaque digest of effective build compatibility;
- `abi_id`: an opaque digest of target and patch ABI;
- an optional default local generation-root hint.

The initial canonical payload is:

```text
nekomata-group-v1
group_id "<opaque-logical-id>"
publication_key "<portable-component>"
baseline_sequence <uint64>
compatibility_id "<opaque-digest>"
abi_id "<opaque-digest>"
[generation_root_hint "<lexical-path>"]
member "<portable/logical/key>"
...
```

All scalar directives except `generation_root_hint` are required exactly once;
the root hint may occur at most once, and at least one member is required.
Canonical serialization emits the order shown. The parser rejects unknown or
duplicate directives, malformed values, and trailing fields.

`publication_key` is one portable ASCII component. Member keys may use `/` to
separate portable components; empty, `.` and `..` components are forbidden.
Members are unique and their declared order is significant. Opaque identity and
location strings are nonempty and contain no ASCII control characters. They are
not interpreted or path-normalized by the payload codec.

This payload is platform-neutral. Executable-section framing, retention, and
application discovery are separate contracts and are not defined by the codec.

Logical identity MUST NOT depend on canonical absolute paths, symlink
expansion, inode numbers, or hardlink identity.

The default generation root is a location hint. A `session_options` override
takes precedence, allowing a moved build tree or container mount to work
without relinking only to change a path.

Identical descriptors with one `group_id` may be deduplicated. Descriptors with
the same `group_id` and different contents are a configuration error.

### 7.1 Compatibility

The runtime MUST NOT compare raw compiler argument strings. Equivalent flags,
response files, and path spelling make that both fragile and insufficient.

The adapter computes `compatibility_id`. It MUST change whenever an effective
property can change generated code or symbol compatibility, including:

- compiler family and version;
- target triple and ABI code-generation options;
- language mode;
- definitions, forced includes, and include resolution;
- optimization, instrumentation, exception, RTTI, and visibility settings;
- reload instrumentation;
- reload-group membership.

Conservative changes are acceptable: an unnecessary restart is safer than
accepting incompatible code. Human-readable build information is diagnostic
only. Ordinary source and header contents are not part of this identity;
changing them is the operation hot reload is meant to accept.

`abi_id` independently covers object format, architecture, endianness, pointer
width, platform ABI, and backend patch ABI.

Neither identity proves that an arbitrary C++ source edit preserves data
layout or behavior. Backend validation and documented restrictions still
reject unsupported globals, vtables, relocations, and other ABI-sensitive
changes.

## 8. Managed publication protocol

The managed protocol uses immutable generation directories and immutable,
uniquely named offers:

```text
<generation_root>/<publication_key>/
  offers/
    <sequence>-<generation_id>.ready
  generations/
    <generation_id>/
      manifest
      objects/
        <object_key>.o
```

The versioned manifest schema contains:

- protocol version;
- group ID, producer sequence, and stream-unique generation ID;
- compatibility and ABI identities;
- exactly one record for every descriptor member;
- each member's key, relative object path, SHA-256 digest, logical source
  identity, and diagnostic build information;
- an optional list of changed logical inputs.

Unknown protocol versions or required fields are rejected. Manifest paths are
relative to the immutable generation directory, normalized, and forbidden
from escaping it.

Membership is exact: every descriptor member occurs once, no unknown member
occurs, and all digests match. Digests establish content integrity, not build
compatibility.

The serialization is an internal, versioned protocol. Its byte grammar must be
documented with the parser implementation before third-party producers are
supported; the semantic schema above is the public design constraint.

### 8.1 Producer

One publication stream has one logical producer. Concurrent publisher
processes for that stream MUST serialize sequence allocation and release under
a stream lock. A sequence is strictly increasing within its stream; a
generation ID is unique within that stream. Sequence gaps are valid after a
failed or cancelled publication.

After the native build has rebuilt affected objects, the publisher:

1. creates a unique staging directory on the publication filesystem;
2. materializes every current object in the group, including unchanged ones;
3. writes and closes the complete manifest;
4. validates membership and digests;
5. releases the directory under its immutable generation name;
6. publishes a unique ready offer with one atomic release operation.

Published contents MUST NOT be modified.

Reflinks and hardlinks are optional optimizations. A hardlink is permitted only
when the adapter can prove that the native build will never modify that inode
in place after publication. Otherwise the publisher uses a reflink or copy.
It MUST fall back to copying, so correctness does not require link support or a
shared source and destination filesystem.

Every publication source defines its atomicity primitive. The local filesystem
source uses an atomic same-filesystem release and makes no claim for arbitrary
network filesystems. Future remote or container transports may implement a
different `generation_source` while preserving the semantic manifest.

Cleanup is separate from publication and consumption. A consumer never renames
or deletes an offer to claim it. The initial implementation performs no
automatic pruning; an explicit cleanup is safe only when no consumer can be
preparing a generation from that stream. Coordinated online retention is a
separate future protocol.

### 8.2 Consumer

Each session keeps its own observed sequence and applied generation per group.
Shared publication state is read-only to consumers.

The initial cursor is the descriptor's `baseline_sequence`, not the newest
offer seen by the first directory scan. The build adapter captures that
high-water mark when it links the executable and serializes that capture with
publication. Consequently stale offers represented by the executable are not
replayed, while an offer published after linking but before `watch()` is not
lost.

For every watched group, the preparation worker:

1. finds offers newer than its local cursor;
2. selects the newest by sequence and deterministic ID tie-break;
3. validates offer, manifest, membership, identities, paths, and digests;
4. parses all objects and resolves the complete cross-TU symbol graph;
5. allocates and relocates the complete candidate image;
6. builds a transaction without changing active entries;
7. moves the transaction into the session's ready queue.

Only one prepared generation per group is retained. A newer valid generation
supersedes older uncommitted work. If the newest observed offer is invalid, it
is reported as rejected; an older offer from the same observation pass is not
silently applied.

An observed offer advances the local cursor whether it is applied or rejected,
so one malformed offer is reported once rather than on every `update()`.
A later valid sequence is still eligible and provides recovery.

Immutable offers are not globally claimed, so multiple compatible processes
may consume the same generation independently.

Prepared-image caching is excluded initially. It may be added only after cache
identity, lifetime, invalidation, and memory accounting are measured and
specified.

## 9. Transaction and threading semantics

Before any function entry is modified, every object in a generation must pass:

- structural parsing;
- target and compatibility checks;
- exact membership validation;
- cross-object symbol and relocation validation;
- patch-plan construction;
- resource-limit checks.

Commit records all data needed to restore each write. If a write fails, every
write already made by that attempt is restored before rejection is reported.

For every function previously redirected by a group but absent from its next
complete generation, commit MUST either restore the baseline entry within the
same transaction or reject the generation. It MUST NOT silently retain a
pointer into the previous prepared image.

A live patch target may be owned by at most one active group. A generation
whose patch plan overlaps a target owned by another group is rejected with a
stable conflict code.

Groups are independent transactions. One group's rejection does not prevent
another ready group from applying in the same `update()`. A call processes at
most one prepared generation per group and all groups ready when the call
begins, in deterministic group order.

The preparation worker MUST NOT redirect code, call application callbacks,
acquire application-owned locks, or claim application threads are quiescent.
Only `update()` commits.

A multithreaded host places `update()` inside its own stop-the-world barrier,
job-system fence, event-loop boundary, or equivalent safe point. Calling it
while another thread may execute code whose entry or active-stack assumptions
are changing is an application error.

This is explicit thread-safe integration, not automatic thread suspension.

## 10. Build-adapter contract

CMake, GN, and Meson expose the same declarations:

- `reload_unit`: owns a native object target and compile configuration;
- `reload_group`: aggregates units, links baseline objects plus a descriptor
  into the application, and defines a native publication target.

Adapters MUST use native dependency graphs. They MUST NOT scrape arbitrary
targets' private build databases or duplicate compiler flags in handwritten
scripts.

One native reload-unit target supplies both the baseline objects linked into
the executable and the objects later published. This prevents compile-command
drift. The adapter also ensures that the generated descriptor is retained by
the final link; correctness MUST NOT depend on incidental static-library
extraction or registration order.

For a group named `demo_hot`, the adapter provides `demo_hot_reload`:

```sh
cmake --build build --target demo_hot_reload
autoninja -C out demo_hot_reload
meson compile -C build demo_hot_reload
```

That target rebuilds native dependencies and invokes the private publisher.
Application code never runs it and never names a ready marker.

The names below are the proposed build API. Exact argument validation and
installation paths must ship with the implementation; the semantics are fixed
here.

## 11. CMake, GN, and Meson cases

Runtime code is identical in all cases: construct the session, call `watch()`,
and call `update()` only at a host safe point.

### 11.1 CMake: single TU

The CMake examples below summarize the common model. Their complete target,
publication, migration, and failure contract is in
[CMake project integration](cmake-integration-design.md).

```cmake
find_package(nekomata CONFIG REQUIRED)

nekomata_add_reload_group(demo_hot
  SOURCES src/tick.cpp
)

add_executable(demo src/main.cpp)
target_link_libraries(demo PRIVATE demo_hot nekomata::backends::elf)
```

The descriptor has one object member. `demo_hot_reload` publishes one object.

### 11.2 CMake: simple multi-TU

```cmake
find_package(nekomata CONFIG REQUIRED)

nekomata_add_reload_group(demo_hot
  SOURCES
    src/gravity.cpp
    src/ball.cpp
)
target_include_directories(demo_hot PRIVATE include)

add_executable(demo src/main.cpp)
target_link_libraries(demo PRIVATE demo_hot nekomata::backends::elf)
```

The sources share one configuration. CMake tracks header dependencies. The
publication target includes both current objects even when only one rebuilds.
No runtime `depfile_planner` is configured.

### 11.3 CMake: complex multi-TU

```cmake
find_package(nekomata CONFIG REQUIRED)

nekomata_add_reload_unit(physics_hot
  SOURCES src/physics/gravity.cpp src/physics/collision.cpp
)
target_link_libraries(physics_hot PRIVATE project_physics_options)

nekomata_add_reload_unit(gameplay_hot
  SOURCES src/gameplay/ball.cpp generated/behaviour.cpp
)
target_link_libraries(gameplay_hot PRIVATE project_gameplay_options)
add_dependencies(gameplay_hot generate_behaviour)

nekomata_add_reload_group(gameplay_group
  UNITS physics_hot gameplay_hot
)

add_executable(game src/main.cpp)
target_link_libraries(game PRIVATE gameplay_group nekomata::backends::elf)
```

Units retain different settings and generated dependencies. The group makes
them one transaction. If they may apply independently, declare two groups.
Atomicity follows group boundaries, not directories or library boundaries.

### 11.4 GN: single TU

```gn
import("//third_party/nekomata/nekomata.gni")

nekomata_reload_group("demo_hot") {
  sources = [ "src/tick.cpp" ]
}

executable("demo") {
  sources = [ "src/main.cpp" ]
  deps = [ ":demo_hot", "//third_party/nekomata:backend_elf" ]
}
```

The template creates the native object target, embeds the descriptor, and
defines `demo_hot_reload`.

### 11.5 GN: simple multi-TU

```gn
import("//third_party/nekomata/nekomata.gni")

nekomata_reload_group("demo_hot") {
  sources = [ "src/gravity.cpp", "src/ball.cpp" ]
  configs = [ ":demo_compile_config" ]
}

executable("demo") {
  sources = [ "src/main.cpp" ]
  deps = [ ":demo_hot", "//third_party/nekomata:backend_elf" ]
}
```

GN/Ninja owns dependency discovery. The reload action depends on every group
output and publishes the complete current set.

### 11.6 GN: complex multi-TU

```gn
import("//third_party/nekomata/nekomata.gni")

nekomata_reload_unit("physics_hot") {
  sources = [ "src/physics/gravity.cpp", "src/physics/collision.cpp" ]
  configs = [ ":physics_config" ]
}

nekomata_reload_unit("gameplay_hot") {
  sources = [ "src/gameplay/ball.cpp", "$target_gen_dir/behaviour.cpp" ]
  configs = [ ":gameplay_config" ]
  deps = [ ":generate_behaviour" ]
}

nekomata_reload_group("gameplay_group") {
  units = [ ":physics_hot", ":gameplay_hot" ]
}

executable("game") {
  sources = [ "src/main.cpp" ]
  deps = [ ":gameplay_group", "//third_party/nekomata:backend_elf" ]
}
```

This has the same unit and transaction structure as CMake. GN only maps native
metadata into the common descriptor and generation schema; it introduces no
GN-specific runtime behavior.

### Meson adapter prerequisite

Meson does not support project-defined functions or methods in `meson.build`.
Nekomata therefore MUST NOT document a fictional helper implemented by an
included `.build` fragment, nor require users to repeat `custom_target()`
publisher plumbing for every group.

The intended interface is a real Meson extension module:

```meson
nekomata = import('nekomata')
nekomata_elf_dep = dependency('nekomata-backend-elf')
```

The module-loading and distribution mechanism must be supported by Meson
itself. Shipping the Meson adapter is blocked until that mechanism is agreed
and tested; CMake invocation, a generated source-tree rewrite, or a
handwritten shell wrapper is not an acceptable substitute.

This constraint follows Meson's documented language model:
<https://mesonbuild.com/Syntax.html#user-defined-functions-and-methods>.

### 11.7 Meson: single TU

```meson
project('demo', 'cpp')

nekomata = import('nekomata')
nekomata_elf_dep = dependency('nekomata-backend-elf')

demo_hot = nekomata.reload_group(
  'demo_hot',
  sources: files('src/tick.cpp'),
)

executable(
  'demo',
  'src/main.cpp',
  dependencies: [nekomata_elf_dep, demo_hot.dependency()],
)
```

The returned holder exposes a dependency containing the baseline object and
embedded descriptor. The module also creates `demo_hot_reload`.

### 11.8 Meson: simple multi-TU

```meson
project('demo', 'cpp')

nekomata = import('nekomata')
nekomata_elf_dep = dependency('nekomata-backend-elf')

demo_hot = nekomata.reload_group(
  'demo_hot',
  sources: files('src/gravity.cpp', 'src/ball.cpp'),
  include_directories: include_directories('include'),
)

executable(
  'demo',
  'src/main.cpp',
  dependencies: [nekomata_elf_dep, demo_hot.dependency()],
)
```

Meson owns header scanning and incremental compilation. The reload target
publishes both current objects after affected inputs rebuild.

### 11.9 Meson: complex multi-TU

```meson
project('game', 'c', 'cpp')

nekomata = import('nekomata')
nekomata_elf_dep = dependency('nekomata-backend-elf')

physics_hot = nekomata.reload_unit(
  'physics_hot',
  sources: files('src/physics/gravity.cpp', 'src/physics/collision.cpp'),
  dependencies: project_physics_dep,
)

gameplay_hot = nekomata.reload_unit(
  'gameplay_hot',
  sources: ['src/gameplay/ball.cpp', generated_behaviour],
  dependencies: project_gameplay_dep,
)

gameplay_group = nekomata.reload_group(
  'gameplay_group',
  units: [physics_hot, gameplay_hot],
)

executable(
  'game',
  'src/main.cpp',
  dependencies: [nekomata_elf_dep, gameplay_group.dependency()],
)
```

Native Meson targets retain heterogeneous compile settings and generated
dependencies. The module converts them to the same common descriptor and
publication protocol; there is no Meson-specific runtime path.

## 12. Ready-marker ownership

Application code never creates `build/neko/generation.ready`.

The native `<group>_reload` target runs the private publisher after all object
dependencies succeed. The publisher stages a complete generation and releases
a uniquely named offer under `offers/`. The linked descriptor tells `watch()`
where to find that stream.

A single shared `generation.ready` is not the managed contract: producers can
overwrite it, consumers can claim it from each other, and its physical path
leaks a transport detail into application code. It may remain available only
through the low-level `manifest_generation_source` compatibility path.

## 13. Templates and optimized builds

Templates need no separate runtime API. Instantiations are symbols in native
objects. Support depends on deterministic handling of their actual linkage,
COMDAT or weak definitions, deduplication, and relocations across the group.

Optimized builds use the same model, but `-O2` changes the observable boundary:

- inlined call sites do not adopt a new out-of-line body automatically;
- interprocedural optimization may remove or merge patch points;
- identical-code folding and section garbage collection affect identity;
- compiler-generated clones need an explicit policy.

The adapter enables any required reload instrumentation and includes it in
`compatibility_id`. General `-O2` support must not be claimed until tests cover
direct and cross-TU calls, inlining boundaries, templates, weak/COMDAT symbols,
and rollback on each supported toolchain.

## 14. TUI

The optional TUI observes `session_snapshot` and can enqueue a reload request.
It MUST NOT call `update()` from its input or rendering thread.

The host receives the request, establishes its safe point, calls `update()`,
and presents the returned events. Polling, a keyboard shortcut, and a headless
loop therefore share one transaction and threading model.

## 15. Required failure behavior

| Condition | Outcome |
| --- | --- |
| `watch()` finds no descriptor | configuration exception |
| unknown `watch(group_id)` ID | configuration exception |
| duplicate identical descriptor | deduplicate |
| duplicate conflicting descriptor | configuration exception |
| generation root or stream absent | idle; retry |
| unknown protocol version | rejected event |
| group, ABI, or compatibility mismatch | rejected event |
| missing, duplicate, or unknown member | rejected event |
| unsafe relative path or digest mismatch | rejected event |
| parse, symbol, or relocation failure | rejected event |
| function disappears without a restorable baseline | rejected event |
| patch target overlaps another group | rejected event |
| commit failure after writes begin | restore all writes; rejected event |
| one group rejects and another is ready | reject one; apply the other |
| `update()` with no enabled group | programming exception |
| two processes observe one offer | both may consume it |

Stable error codes and rejection messages become API contracts when released.
Tests must cover both.

## 16. Resource bounds

A session has configurable limits for manifest bytes, objects per group, bytes
per object and generation, symbols, relocations, prepared generations, and
retained diagnostics.

An artifact exceeding a limit is rejected before commit. An allocation failure
that leaves the session unusable follows the fatal error path.

`update()` handles all groups ready at call entry, at most one generation per
group. Expensive work stays off the commit path. A time-budgeted commit API may
be considered later; this design does not claim hard real-time bounds.

## 17. Current implementation and migration

The current tree contains parts of this model: `reload_session`, ELF backend
construction, direct source/object watching, generation manifests, depfile
planning, and group preparation.

It does not implement this complete managed contract. In particular,
`generation_watch`, the v1 ready marker, public planner setup, and the current
boolean/exception result model are compatibility mechanisms, not the desired
application API.

Migration order:

1. add descriptor, group-state, event, snapshot, and stable error-code types;
2. add the immutable multi-consumer protocol and parser tests;
3. add descriptor registration and generation-root resolution;
4. separate background preparation from safe-point commit;
5. add the CMake group integration;
6. add heterogeneous CMake units and remove handwritten reload scripts from
   managed examples;
7. add equivalent GN templates;
8. resolve the Meson extension-module distribution prerequisite and implement
   the same unit/group semantics;
9. deprecate ambiguous watch overloads only after replacements ship;
10. add caches only if profiling demonstrates a need.

Each change should carry focused tests without changing unrelated behavior.

## 18. Acceptance criteria

The design is complete only when automated tests demonstrate:

- identical application runtime code for all nine build cases;
- no paths, depfiles, object lists, or markers in ordinary application code;
- single-TU and multi-TU complete publication;
- exact-membership rejection and cross-TU all-or-nothing rollback;
- compatible cross-TU symbol resolution;
- independent group success and rejection in one `update()`;
- build and ABI mismatch rejection;
- two processes consuming the same immutable offer;
- generation-root override after moving a build tree;
- identity stability through symlinked source and build paths;
- copy fallback when reflink and hardlink are unavailable;
- native header and generated dependencies in CMake, GN, and Meson;
- template and supported optimized-build cases;
- worker preparation never committing outside `update()`;
- a host-controlled multithread safe point;
- TUI requests reaching that same host-controlled `update()`;
- recovery from rejection with a later valid generation;
- no supported driver CLI or handwritten reload scripts in managed examples.

These criteria separate a convenient demonstration from a dependable project
integration model.
